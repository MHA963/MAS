## CORE DEFINITIONS


### What is planning in MAS?
Planning is a **search through a set of tasks** to find a **sequence** that brings the system from an **initial state** to a **goal state**.[1]

**Key distinctions:**
- **Plan:** An ordered set of tasks answering "what/how"—the sequence of actions to execute[1]
- **Schedule:** Adds timing and concurrency to a plan, answering "who/when"—allows tasks to be performed concurrently on a timeline[1]
- **MAS planning/scheduling:** Extends to multiple agents' task streams plus cross-agent constraints (dependencies, resource sharing, cooperation)[1]


### What is Multi-Robot Task Allocation (MRTA)?
MRTA is the problem of allocating a set of tasks to a set of robots/agents subject to constraints, while optimizing an objective function (e.g., minimize time, cost, or maximize tasks completed).[1]

**Core challenge:**
Given heterogeneous agents, tasks, and constraints, decide **who does what** to optimize a given objective while respecting imposed constraints.[1]


### What MAS mission planning is NOT
The slides explicitly distinguish MAS mission planning from:[1]
- Path planning (finding collision-free paths)
- Motion planning (computing trajectories respecting dynamics)
- Path following (control to track a path)
- Path finding (graph search for routes)

Mission planning operates at a higher level: **task sequencing and allocation**, not low-level trajectory generation.

## WHY MULTI-AGENT PLANNING IS HARDER


### Compared to single-agent planning, MAS adds:[1]

| Single-Agent | Multi-Agent |
|--------------|-------------|
| No task allocation needed | **Task allocation:** Who does what? |
| No cross-schedule dependencies | **Cross-schedule dependencies:** Agent A's task may depend on Agent B's completion |
| Straightforward objective | **More complex objectives:** e.g., minimax (fairness), resource balancing |
| Simple constraints | **Constrained resources, cooperation requirements, task dependencies** |
| Homogeneous (one agent) | **Potential heterogeneity and coalition formation** |


### Additional MAS constraints:[1]
1. **Constrained resources:** Resources are not infinite (battery, tools, communication bandwidth)
2. **Agent cooperation:** Some tasks require more than one agent to complete (e.g., lift heavy object)
3. **Task dependencies:** Completion of one task may depend on another task finishing first (precedence)

## MRTA TAXONOMIES: HOW TO CLASSIFY PROBLEMS


### 1. Gerkey & Mataric (2004)[2][1]

Three orthogonal dimensions:

| Dimension | Types | Meaning |
|-----------|-------|---------|
| **Allocation type** | IA vs TA | **Instantaneous Assignment (IA):** one-shot allocation; **Time-extended Assignment (TA):** build routes/sequences over time |
| **Task type** | SR vs MR | **Single-Robot Tasks (SR):** one agent per task; **Multi-Robot Tasks (MR):** coalitions needed |
| **Concurrency** | ST vs MT | **Single-Task Robots (ST):** one task at a time; **Multi-Task Robots (MT):** can handle multiple tasks concurrently |

**Exam insight:** These dimensions predict solution complexity. IA problems often reduce to one-shot assignment (e.g., auction); TA requires planning routes and schedules (e.g., MTSP). MR tasks imply coalition formation and cross-schedule dependencies.


### 2. Korsah et al. (2013)[3][1]

**Degree of interrelatedness (dependencies):**

| Type | Meaning |
|------|---------|
| **ND (No Dependencies)** | Tasks are independent; simple parallel execution |
| **ID (Intra-Schedule Dependencies)** | Dependencies within one agent's schedule (precedence within agent) |
| **XD (Cross-Schedule Dependencies)** | Dependencies across agents (Agent A's task depends on Agent B's completion) |
| **CD (Complex Dependencies)** | Nonlinear utility interactions, coalition utilities, complex constraints |

**Exam insight:** As you move from ND → ID → XD → CD, coordination complexity explodes. XD/CD typically require constraint-heavy scheduling or negotiation, not just greedy assignment.


### 3. Nunes et al. (2017)[1]

Additional practical flags:
- **Time-Windows (TW):** Tasks must be completed within specific time intervals
- **Synchronization/Precedence (SP):** Tasks must be synchronized or ordered

**Exam insight:** These flags push you away from "just minimize travel distance" into constraint satisfaction scheduling, often requiring exact solvers or specialized heuristics.

## MTSP: MULTI-AGENT TRAVELING SALESMAN PROBLEM


### Definition[1]
- **TSP:** One tour visits all cities/tasks, minimizing path cost
- **MTSP:** Extends TSP to **m agents** servicing **n tasks**

**Formulation:**
- \( m \) agents (salesmen)
- \( n \) tasks (cities)
- \( w_{ij} \): cost/distance from task \(i\) to task \(j\) (stored in adjacency matrix)
- \( x_{ij} \): binary decision variable = 1 if agent travels from \(i\) to \(j\), 0 otherwise


### Typical objective functions[1]

| Objective | Meaning | Behavior |
|-----------|---------|----------|
| **Minimax** | Minimize the interval from start of first task to end of last task (makespan) | Favors using more agents to balance load; minimizes longest tour |
| **Minisum** | Minimize total cost across all tours | May leave some agents idle; minimizes total distance |
| **Combinations** | Weighted combinations of minimax + minisum, fairness metrics, etc. | Tunable trade-offs |

**Formally (minimax):** 
\[
\min_{x} \max_{s \in \text{agents}} (\text{tour length of agent } s)
\]


### Typical constraints[1]

1. **Entry/exit exactly once:** Each task node has exactly one entry and one exit (one agent visits)
   \[
   \sum_{j} x_{ij} = 1, \quad \sum_{i} x_{ij} = 1 \quad \forall \text{ task } j
   \]
2. **Depot start/end:** Agents start at a source depot and end at a destination depot
3. **No self-loops:** \( x_{ii} = 0 \)
4. **Same agent enters/exits:** Flow conservation—same agent that enters a city must exit it
5. **Subtour elimination:** Prevent disconnected sub-cycles (Miller-Tucker-Zemlin constraints or similar)

**Extensions (mentioned in slides):**[1]
- **Precedence constraints:** Task \(j\) can only be performed after task \(i\)
- **Capacity/quantity constraints:** An agent can carry/handle only a limited number of tasks or payload

## HOW TO SOLVE MRTA/MTSP: EXACT VS METAHEURISTIC


### Exact Methods (e.g., MILP)[1]

**Characteristics:**
- **Guaranteed optimal solution**
- **Worst-case guarantees** on solution quality
- **Very slow** for large instances (exponential in worst case)
- **No anytime-stop option:** Must run to completion for guarantee

**Example solvers:** CPLEX, Gurobi[1]

**When to use:**
- Small to medium problem sizes
- When optimality is critical (e.g., high-cost missions, safety-critical)
- Offline planning with time to compute

**Typical limit (mentioned in slides):** Around 35-40 tasks depending on constraints and solver license[1]


### Metaheuristics (e.g., Genetic Algorithms)[1]

**Characteristics:**
- **Fast**
- **Anytime-stop option:** Can be interrupted at any time and return best-so-far solution
- **No guaranteed optimal solution**
- **No formal solution quality guarantees**

**When to use:**
- Large problem instances
- Real-time or dynamic replanning needs
- Complex constraints where exact methods are infeasible
- "Good enough quickly" beats "optimal too late"


### Brute Force[1]
- Compute all possible combinations
- Pick the one satisfying objective (e.g., min cost)
- **Only works for tiny instances** (factorial explosion)

## GENETIC ALGORITHM (GA) APPROACH FOR MTSP


### Encoding[1]
- **Chromosome (individual):** A permutation of tasks representing a tour or set of tours
- Example: `[Gliwice, Cairo, Rome, Krakow, Paris, Alexandria, Berlin, Tokyo, Hong Kong, Rio]`
- For multiple agents: chromosome encodes how tasks are partitioned among agents


### GA workflow[1]
1. **Initial population:** Random individuals (tours), specify population size
2. **Fitness evaluation:** Evaluate each individual against objective function (e.g., tour length, minimax)
3. **Selection:** Higher fitness individuals have higher selection chance (e.g., tournament, roulette wheel)
4. **Crossover:** Combine two parents to create offspring
   - **Ordered crossover** preserves permutation validity (copy segment from parent 1, fill remaining from parent 2 in order)
5. **Mutation:** Random changes to preserve diversity
   - **Switch mutation:** Swap two cities in tour
6. **Repeat** for multiple generations until convergence or time limit


### Why ordered crossover?[1]
Naive crossover (cut-and-splice) breaks permutation constraints—can duplicate or miss cities. Ordered crossover:
- Copy a segment from parent 1
- Fill remaining positions with cities from parent 2 in the order they appear, skipping already-placed cities
- Guarantees valid permutation


### Minimax variant behavior[1]
Minimax objective "favors utilization of more agents"—it tries to balance load, so adding agents can reduce the maximum tour length even if total distance increases.

## MODELING ASSUMPTIONS (EXAM-FRIENDLY)


When formalizing MRTA/MTSP, the slides suggest stating these assumptions to clarify problem scope:[1]

1. **No obstacles in the environment** (or obstacles handled at motion planning layer)
2. **Communication is perfect** (no delays, packet loss, or bandwidth limits)
3. **All states are fully observable** (agents know task locations, costs, other agents' states)
4. **Physical properties of robots are ignored, except for velocity** (no dynamics, just travel time)
5. **No partial task execution is possible** (tasks are atomic—either done or not)
6. **Task properties are known a priori** (costs, locations, requirements known before planning)

**Exam strategy:** State these assumptions up front in problem formulation to bound the mission-planning problem and prevent scope creep into perception/control/physics. Acknowledge what would change if assumptions are relaxed.

## REPLANNING WHEN ROBOTS FAIL


### Trigger: What if a robot goes missing?[1]
**Answer: Replan.**


### Key design questions[1]

| Question | Options | Trade-offs |
|----------|---------|-----------|
| **Who replans?** | Central planner vs Local agents | Central = optimal but single point of failure, communication bottleneck; Local = robust, scalable but risk of conflicts |
| **Detection of failure** | Full vs Partial | Full detection (all agents know) enables coordinated replan; partial (only neighbors know) is realistic but harder to coordinate |
| **Exchange of information** | Local vs Global view | Global view enables optimal replan but high communication cost; local view is scalable but may miss dependencies |
| **Handling double allocations** | Locking/claims, auctions, central arbiter | Prevent two agents claiming same task; distributed mechanisms vs central coordination |
| **Communication costs** | Bandwidth, latency, energy | High communication for global replan may be infeasible in bandwidth-limited or energy-constrained scenarios |


### Hybrid replanning[1]
**Key idea:** Decide **when to call the global planner** vs **when to let agents solve issues locally**.

**Example policy:**
- **Local resolution:** If only one agent fails and its tasks can be redistributed to immediate neighbors without violating hard constraints → local negotiation/auction
- **Global replanning:** If failure cascades (multiple agents affected), or hard constraints violated (precedence, deadlines) → invoke central MILP solver or global heuristic

**Exam question:** "When should we call the planner and when should we let agents solve issues locally?"[1]
**Answer framework:** 
- Local if: failure is isolated, no cross-schedule dependencies violated, low communication cost, agents have capacity
- Global if: cascading failures, tight coupling (XD/CD dependencies), time-critical with hard deadlines, need optimality guarantee

## COMPLETE EXAM QUESTIONS & ANSWERS


### Q1: What is the difference between planning and scheduling in MAS?
**Answer:**
Planning is a search through a set of tasks to find a sequence that leads from the initial state to the goal state—answering "what/how" to do. Scheduling adds timing and allows concurrency, answering "who/when" tasks happen on a timeline. For MAS, planning spans multiple agents' task streams, and scheduling adds cross-agent constraints, resource sharing, and cooperation requirements.[1]


***


### Q2: Why is multi-agent planning harder than single-agent planning?
**Answer:**
Multi-agent planning adds: (1) task allocation—deciding who does what; (2) cross-schedule dependencies—one agent's task may depend on another's completion; (3) more complex objective functions and constraints, such as constrained resources, cooperation requirements, and task dependencies; (4) potential heterogeneity and coalition formation. Single-agent planning has none of these: no allocation, no cross-dependencies, straightforward objective.[1]


***


### Q3: What is MRTA and how is it classified?
**Answer:**
MRTA is multi-robot task allocation: allocating tasks to robots/agents under constraints to optimize an objective. It is classified by: (1) Gerkey & Mataric dimensions—allocation type (IA vs TA), task type (SR vs MR), concurrency (ST vs MT); (2) Korsah's dependency levels—ND, ID, XD, CD; and (3) Nunes's time windows (TW) and synchronization/precedence (SP). These taxonomies predict solution complexity and guide solver choice.[2][3][1]


***


### Q4: Explain the Gerkey & Mataric taxonomy dimensions with examples.
**Answer:**
(1) **IA vs TA:** Instantaneous assignment (one-shot, e.g., auction) vs time-extended (build routes, e.g., MTSP). (2) **SR vs MR:** Single-robot tasks (one agent per task) vs multi-robot tasks (coalitions needed, e.g., two robots lift together). (3) **ST vs MT:** Single-task robots (one task at a time) vs multi-task robots (handle multiple concurrently). Example: TA-SR-ST = vehicle routing (time-extended, single robot per delivery, one delivery at a time).[2][1]


***


### Q5: What is the difference between ND, ID, XD, and CD dependencies (Korsah taxonomy)?
**Answer:**
**ND (No Dependencies):** Tasks are independent; simple parallel execution. **ID (Intra-Schedule):** Dependencies within one agent's schedule (e.g., task B after task A for same agent). **XD (Cross-Schedule):** Dependencies across agents (Agent A's task depends on Agent B's completion). **CD (Complex):** Nonlinear utility interactions, coalition utilities, or complex constraints. As you move ND → CD, coordination complexity increases, requiring richer scheduling and negotiation.[3][1]


***


### Q6: What is MTSP and how does it differ from TSP?
**Answer:**
TSP (Traveling Salesman Problem) is one tour visiting all cities minimizing path cost. MTSP (Multi-agent TSP) extends this to \(m\) agents servicing \(n\) tasks, with costs \(w_{ij}\) between tasks and binary decision variables \(x_{ij}\) (1 if agent travels from \(i\) to \(j\)). MTSP adds task allocation (who visits which tasks) and multiple concurrent tours, making it a routing + allocation hybrid.[1]


***


### Q7: What are typical MTSP objective functions and their implications?
**Answer:**
**Minimax:** Minimize the interval from start of first task to end of last task (makespan)—favors using more agents to balance load. **Minisum:** Minimize total cost across all tours—may leave agents idle, focuses on total distance. **Combinations:** Weighted trade-offs or fairness metrics. Minimax tends to spread work; minisum optimizes aggregate efficiency.[1]


***


### Q8: What are the key constraints in MTSP formulation?
**Answer:**
(1) Each task node has exactly one entry and one exit (one agent visits). (2) Agents start at a source depot and end at a destination depot. (3) No self-loops (\(x_{ii} = 0\)). (4) Same agent enters and exits a task (flow conservation). (5) Subtour elimination (prevent disconnected cycles). Extensions include precedence constraints (task \(j\) after task \(i\)) and capacity constraints (limited tasks per agent).[1]


***


### Q9: Compare exact methods and metaheuristics for solving MTSP/MRTA.
**Answer:**
**Exact methods (e.g., MILP with CPLEX/Gurobi):** Guaranteed optimal solution, worst-case guarantees, but very slow and no anytime-stop option—must run to completion. Best for small-medium instances when optimality is critical. **Metaheuristics (e.g., GA):** Fast, anytime-stop (return best-so-far), but no optimality guarantee or solution quality bounds. Best for large instances, real-time replanning, or when "good enough quickly" beats "optimal too late".[1]


***


### Q10: When would you choose GA over MILP for MRTA?
**Answer:**
Choose GA when: (1) problem size is large (MILP becomes infeasible); (2) real-time or dynamic replanning is needed (anytime property); (3) complex constraints make exact solving slow; (4) acceptable solution quality trade-off for speed; and (5) can stop computation at any time and use best-so-far. Example: online task allocation in dynamic environment where tasks arrive continuously.[1]


***


### Q11: What is ordered crossover in GA and why is it needed for routing problems?
**Answer:**
Ordered crossover is a genetic algorithm operator that combines two parent tours to create valid offspring permutations. It works by: (1) copying a segment from parent 1, (2) filling remaining positions with cities from parent 2 in order, skipping already-placed cities. It is needed because naive crossover (cut-and-splice) breaks permutation constraints—duplicates or misses cities. Ordered crossover preserves validity: every city appears exactly once.[1]


***


### Q12: Explain how GA workflow applies to MTSP.
**Answer:**
(1) **Encoding:** Chromosome = permutation of tasks (tour or partitioned tours for multiple agents). (2) **Initial population:** Random tours, fixed population size. (3) **Fitness evaluation:** Score each tour by objective (e.g., tour length, minimax). (4) **Selection:** Higher fitness individuals more likely selected (tournament/roulette). (5) **Crossover:** Ordered crossover combines parents preserving permutation. (6) **Mutation:** Switch mutation swaps two tasks. (7) **Repeat** generations until convergence or time limit.[1]

### Q13: What modeling assumptions should you state when formalizing MRTA/MTSP for an exam?
**Answer:**
State: (1) No obstacles (or handled separately); (2) perfect communication; (3) fully observable states; (4) ignore robot physics except velocity; (5) no partial task execution; (6) task properties known a priori. These assumptions clarify problem scope, bound the mission-planning problem, and prevent scope creep into perception/control. Acknowledge what would change if assumptions are relaxed (e.g., partial observability requires belief tracking).[1]


***


### Q14: Why does minimax objective favor using more agents?
**Answer:**
Minimax minimizes the longest tour (makespan—interval from start of first task to end of last task). Adding more agents allows spreading tasks more evenly, reducing the maximum load on any single agent. Even if total distance increases (more agents travel), the longest individual tour decreases, improving minimax objective. This balances workload but may increase aggregate cost.[1]


***


### Q15: What are precedence and capacity constraints in MTSP?
**Answer:**
**Precedence constraints:** Task \(j\) can only be performed after task \(i\) (e.g., "unlock door" before "enter room"). Adds ordering dependencies within or across agent schedules. **Capacity constraints:** An agent can carry/handle only a limited number of tasks or payload (e.g., delivery truck capacity). Both are extensions beyond basic MTSP and increase problem complexity, often requiring constraint programming or specialized solvers.[1]


***


### Q16: What are the key design choices in replanning after a robot failure?
**Answer:**
(1) **Who replans?** Central planner (optimal but bottleneck) vs local agents (robust but risk of conflicts). (2) **Detection:** Full (all agents know) vs partial (only neighbors). (3) **Information exchange:** Local view (scalable) vs global view (optimal but high communication). (4) **Double allocations:** Prevent via locking/claims, auctions, or central arbiter. (5) **Communication costs:** Bandwidth, latency, energy trade-offs. Choose based on failure scope, dependencies, and resource constraints.[1]


***


### Q17: Explain hybrid replanning with a concrete policy.
**Answer:**
Hybrid replanning decides when to invoke a global planner vs let agents resolve locally. **Policy example:** Use **local resolution** if failure is isolated (one agent, tasks can be redistributed to neighbors without violating hard constraints)—agents negotiate or auction tasks locally. Use **global replanning** if failure cascades (multiple agents affected), or hard constraints are violated (precedence, deadlines, cross-schedule dependencies), or optimality is critical—invoke central MILP solver or global GA. Balances responsiveness, communication cost, and solution quality.[1]


***


### Q18: Classify this scenario using MRTA taxonomies: "2 robots must lift a heavy box together, then one robot delivers it; tasks have deadlines."
**Answer:**
**Gerkey & Mataric:** TA (time-extended, involves routes/sequences), MR (multi-robot task—lifting requires two robots), MT (robots can handle multiple tasks over time). **Korsah:** At least XD (cross-schedule dependencies—lifting depends on both robots' schedules) or CD if utility/deadline interactions are complex. **Nunes:** TW (time windows—deadlines), SP (precedence—deliver after lift, synchronization for joint lifting). This is a complex MRTA instance requiring constraint-heavy scheduling.[1]


***


### Q19: Why do MR tasks (coalitions) often imply cross-schedule dependencies?
**Answer:**
MR tasks require multiple robots to execute together (e.g., lift heavy object). This creates synchronization requirements—robots must arrive at the task location at the same time and coordinate execution. Even if travel costs are independent, the task execution itself couples the agents' schedules: Agent A's schedule depends on when Agent B can participate. This moves the problem into at least XD (cross-schedule dependencies), increasing coordination complexity.[1]


***


### Q20: What makes MTSP with time windows harder than basic MTSP?
**Answer:**
Time windows (TW) add constraints that tasks must be completed within specific time intervals. This transforms the problem from pure cost minimization into constraint satisfaction + optimization. Solutions must respect temporal feasibility: a tour may be shortest but infeasible if it arrives too late. Solvers must check/enforce time window constraints, often requiring time-indexed variables or constraint programming techniques, increasing computational complexity significantly.[1]


***


### Q21: What is the typical limit for exact MTSP solvers like CPLEX, and why?
**Answer:**
The slides mention a limit around 35-40 tasks for CPLEX MILP solver, depending on constraints and solver license (free version has stricter limits). The "why" is that MTSP is NP-hard—worst-case exponential complexity. As the number of tasks and agents grows, the branching factor and constraint complexity explode, making exact solving intractable within reasonable time. Beyond this limit, metaheuristics like GA are preferred.[1]


***


### Q22: How do you prevent double allocations in distributed replanning?
**Answer:**
Mechanisms include: (1) **Locking/claims:** Agent claims a task and others must check/respect claims before allocating (requires communication). (2) **Auctions:** Tasks are auctioned; winning bid is broadcast to prevent others from taking same task. (3) **Central arbiter:** One designated agent or base station maintains "source of truth" allocation and resolves conflicts. (4) **Consensus protocols:** Agents negotiate to agree on allocation. Choice depends on communication topology, failure model, and real-time requirements.[1]


***


### Q23: When should failure detection be "full" vs "partial"?
**Answer:**
**Full detection:** All agents immediately know when one fails—enables coordinated global replan, optimal reassignment, but requires reliable broadcast and assumes communication is perfect. **Partial detection:** Only neighboring or affected agents detect failure—more realistic in bandwidth-limited, distributed settings, but harder to coordinate (may have inconsistent views, double allocations). Use full when communication is reliable and speed matters; use partial when communication is limited or system must be robust to communication failures.[1]


***


### Q24: Give a concrete MTSP example with initial state, tasks, objective, and one constraint.
**Answer:**
**Example:** 3 delivery robots, 9 delivery tasks (packages) in a city grid. **Initial state:** All robots at central depot. **Tasks:** Deliver packages to 9 locations. **Objective:** Minimax—minimize the time until the last robot finishes (balance load). **Constraint:** Each package location visited exactly once; robots return to depot when done. **Formulation:** \(m=3\) agents, \(n=9\) tasks, \(w_{ij}\) = travel time between locations, \(x_{ij}\) = binary routing variables. Use MILP or GA to solve.[1]


***


### Q25: What is the difference between MAS mission planning and path planning?
**Answer:**
**Mission planning:** High-level task sequencing and allocation—deciding which agent does which tasks in what order to achieve mission objectives. Operates at task level (e.g., "visit waypoint A, then B"). **Path planning:** Low-level computation of collision-free trajectories or routes in configuration space to move from one location to another. Operates at geometric/control level. Mission planning answers "what tasks and who"; path planning answers "how to physically get there".[1]


***


### Q26: Why is "anytime" property important for metaheuristics in MAS?
**Answer:**
In dynamic MAS environments, tasks may arrive, agents may fail, or situations may change while computing a plan. The "anytime" property means the algorithm can be interrupted at any moment and return the best solution found so far—valid and usable, though not necessarily optimal. This allows real-time responsiveness: if time runs out or situation changes, use current best plan and replan later. Exact methods must run to completion for guarantees, making them unsuitable for time-critical, dynamic scenarios.[1]


***


### Q27: What happens if you relax the "no partial task execution" assumption?
**Answer:**
If partial task execution is allowed, tasks can be preempted or split across agents. This changes the model: (1) need to track task progress/state; (2) allocation becomes more flexible (agents can share tasks or resume interrupted work); (3) constraints must handle synchronization/handoff; and (4) objective functions may account for overhead of splitting. Increases expressiveness but also complexity—may require scheduling with preemption or task decomposition mechanisms.[1]


***


### Q28: How does heterogeneity in agents affect MRTA formulation?
**Answer:**
Heterogeneous agents have different capabilities (speed, sensors, tools, battery). This affects: (1) task feasibility—not all agents can do all tasks (add capability constraints); (2) cost matrices \(w_{ij}\) become agent-specific \(w_{ij}^k\) (Agent \(k\)'s cost from task \(i\) to \(j\)); (3) allocation decisions must consider specialization (assign tasks to capable/efficient agents); and (4) coalition formation for MR tasks (which combinations of agents can perform task?). Homogeneity simplifies; heterogeneity increases search space and constraint complexity.[1]


***


### Q29: What is subtour elimination and why is it needed in MTSP?
**Answer:**
Subtour elimination prevents solutions where an agent's route forms disconnected cycles (visiting a subset of tasks in a closed loop without returning to depot or connecting to other tasks). Without subtour elimination, you can get invalid solutions like: Agent 1 tours {A, B, A} and Agent 2 tours {C, D, C}, leaving tasks unconnected. Miller-Tucker-Zemlin (MTZ) constraints or similar are added to the MILP formulation to ensure each agent's tour is a single connected path from depot to depot visiting assigned tasks exactly once.[1]


***


### Q30: Explain the concept of "coalition formation" in MAS planning.
**Answer:**
Coalition formation is when multiple agents temporarily group to perform a task requiring joint effort (MR tasks). Example: two robots lift a heavy object together. Coalition formation involves: (1) identifying which tasks need coalitions; (2) deciding which agents join which coalitions (considering capabilities, locations, availability); (3) coordinating coalition members' schedules (synchronization); and (4) potentially negotiating or bidding for coalition membership. Adds complexity because allocation is no longer 1-to-1 (task-to-agent) but many-to-many with synchronization constraints.[1]

## ADVANCED / DEEPER EXAM QUESTIONS


### Q31: How do you model cross-schedule dependencies (XD) formally in MTSP?
**Answer:**
Cross-schedule dependencies mean one agent's task depends on another agent's task completion. Formally: Add precedence constraints across agents. Example: Task \(j\) assigned to Agent \(k_2\) can only start after Task \(i\) assigned to Agent \(k_1\) finishes. Introduce time variables \(t_i^k\) (time Agent \(k\) completes task \(i\)), and add constraint:
\[
t_i^{k_1} + \text{travel time from } i \text{ to } j \leq t_j^{k_2}
\]
if \(i\) must precede \(j\) across agents. This couples agents' schedules and increases MILP complexity.[3][1]


***


### Q32: What is the trade-off between minimax and minisum objectives in terms of fairness and efficiency?
**Answer:**
**Minimax (fairness):** Minimizes the longest tour (makespan), balancing load across agents—promotes fairness, no agent overworked. May increase total distance (efficiency loss) by assigning tasks suboptimally to spread work. **Minisum (efficiency):** Minimizes total cost across all tours, optimizing aggregate efficiency—may leave some agents idle or underutilized (unfair). Trade-off: fairness vs efficiency. Choose minimax when load balance matters (e.g., battery constraints, fairness goals); choose minisum when total resource use matters (fuel cost, time-aggregate).[1]


***


### Q33: How would you handle dynamic task arrival in MTSP (tasks appear during execution)?
**Answer:**
Use **online/dynamic MRTA** approaches: (1) **Rolling horizon:** Replan periodically with known tasks, commit to near-term assignments, defer far-future. (2) **Anytime heuristic:** Use GA or greedy insertion that can quickly update plan when new task arrives. (3) **Auction-based:** New task triggers auction among agents; winner inserts task into route. (4) **Hybrid local/global:** Local agents handle small changes (insert nearby tasks); global replanner invoked if significant disruption. Key: balance responsiveness (fast replan) with solution quality.[1]


***


### Q34: What communication topology is best for distributed MRTA replanning, and why?
**Answer:**
**Fully connected (all-to-all):** Enables fast global information sharing and optimal coordination, but high bandwidth/energy cost, doesn't scale. **Hierarchical (leader-based):** Leader aggregates info and coordinates; reduces messages but single point of failure and bottleneck. **Peer-to-peer (local neighbors):** Scalable, robust to failures, low bandwidth, but slower convergence and risk of conflicts/inconsistency. **Best choice depends on:** system size, communication constraints, failure model, and real-time requirements. For small teams with reliable comms, use fully connected; for large swarms or bandwidth-limited, use local peer-to-peer.[1]


***


### Q35: Explain a scenario where local replanning is sufficient vs one where global replanning is needed.
**Answer:**
**Local sufficient:** One robot in a 10-robot warehouse delivery team has low battery and stops. Its 3 nearby tasks can be reassigned to immediate neighbors who have capacity and are close by. No precedence constraints violated, minimal communication (neighbors negotiate), fast resolution. **Global needed:** In a 5-robot construction site, one robot fails while performing a task that is a precedence requirement for 3 other agents' tasks (e.g., welding a joint before others can install panels). Failure cascades, tight coupling (XD dependencies), need global MILP replan to find feasible reassignment respecting precedence and deadlines.[1]
